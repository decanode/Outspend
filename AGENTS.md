## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Project architecture (read this before changing structure)

Outspend is a plain-JavaScript, offline-first expense tracker for **Android (full automatic SMS capture) and iPhone (manual capture: the user shares a bank message to a Shortcut, which opens `outspend://capture?text=...`)**. The generic Expo-starter guidance above is overridden where it conflicts with this section.

- **iOS specifics:** iPhone can never read SMS, so SMS code is Android-only and guarded by `Platform.OS`/`isSmsAvailable`. iPhone capture is `useCaptureLink` -> `SharedCapture.js` -> `SmsIngest.handleSharedText` (same parser, sender check skipped, always confirmed by the user first). `android/` is committed, `ios/` is generated by EAS (gitignored); iOS native config lives in `app.json` (including the `simdjson` pod WatermelonDB needs, via `expo-build-properties`). WatermelonDB uses the bridge adapter on iOS (`jsi` is Android-only until verified on a device).
- **Navigation:** React Navigation bottom tabs in `App.js`. We deliberately do **not** use Expo Router: the app is a bare-workflow project with a custom Kotlin SMS module, and `android/` is committed and edited by hand (the "never edit `ios/`/`android/`" rule does not apply here).
- **Data:** WatermelonDB (SQLite). Schema/migrations in `src/db/`. Screens never write to the DB directly; use the helpers in `src/data/`.
- **Pure logic** (parser, rules, analytics, subscription detection, export formatting, access/trial) lives in `src/services/` with no native or DB imports, and is unit-tested in `__tests__/`. Keep it that way.
- **SMS pipeline:** live: `SmsReceiver.kt` (manifest receiver, fires even when the app is closed) -> `SmsHeadlessTaskService.kt` -> JS task `SmsReceivedTask` (`index.js`) -> `SmsIngest.handleIncomingSms`. Catch-up/history: `SmsModule.getInboxSince` -> `src/native/Sms.js` -> `SmsIngest.js`. Both end in `TransactionManager.js` (commit) <- `IngestPlanner.js` (pure plan). Every SMS gets a stable `external_id`, so imports are idempotent. Unknown payees trigger a notification with a reply box (`NotificationService.js`).
- **Insights/planning logic** is pure and tested: `Insights.js` (periods, analysis, trends), `Budgets.js`, `Anomaly.js`, `Planning.js` (salary, upcoming bills, splits, tags), `TransferDetector.js`. Spend always goes through `Analytics.spendEntries` so transfers are excluded and split shares are honoured; never sum `amount` directly for analytics.
- **"This month" is not always a calendar month.** Once the user confirms a salary source, spending periods are pay cycles (salary credit to salary credit, matched by sender, never by amount). Use `resolveMonthPeriod()` / `currentBudgetPeriod()` (`PayCycle.js`, `data/payCycle.js`) for Analytics, budgets, Home and the widget; never call `makePeriod('MONTH')` directly for "the current month".
- **Lists must use `watch()`** (`src/data/util.js`) or an `observe*` helper, not a bare `query`, otherwise they do not refresh after an edit.
- **After anything that changes transactions** call `afterChange()` (`PostChange.js`): it pairs transfers, checks budgets and refreshes the widget.
- **Not tied to one currency or country.** Everything country-specific lives in `src/regions/` (currency table, region presets, SMS profiles). Never hard-code `₹`, `INR`, `en-IN`, "Rs", UPI or amount thresholds in logic or UI: use `formatMoney()`, `currencySymbolFor()`, `homeCurrency()`, `dateLocale()`, `scaled(inrAmount)` for thresholds, and `parseNumber`/`parseAmount` for input. One home currency per install; a transaction in another currency carries `currency` and is excluded from home totals (`isForeignCurrency`). To add a country: add a row to `REGIONS` (and an SMS profile if its messages differ), add real anonymised samples to `__tests__`, run the tests.
- **Privacy is a product constraint:** no analytics, no remote logging, no network calls with user data. SMS and receipts stay on the device.
- **Settings/flags:** persisted app state in `src/services/Settings.js`; release switches in `src/config.js` (`enforcePaywall`).

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
